# 0001. Запис запусків і позначок «done» — лише через функції `private` (security definer)

- Статус: прийнято (уточнює D5 і D6 з `openspec/changes/impl-ws6-runs/design.md`)
- Дата: 2026-10-20
- AC: AC-RUN-01, AC-RUN-02, AC-RUN-04, AC-RUN-08, AC-RUN-09, AC-TASK-01, AC-TASK-02, AC-TASK-03, AC-TASK-07

## Контекст

`design.md` (D5, D6) передбачав функції `public.launch_run` і `public.mark_task_done` як `security invoker` з
`grant insert`/`update` для `authenticated` і політиками RLS на `insert`/`update`. Рев'ю CodeRabbit до PR задачі 1
показало, що такі гранти дозволяють писати в `runs` і `run_tasks` напряму через Data API, в обхід функцій: політики
перевіряють лише, **хто** пише, а не чи рядок відповідає шаблону. Наслідки: менеджер запуску може дописати в запуск
задачу після запуску (ламає знімок — AC-RUN-02, і правило «виконавців задають лише під час запуску»), підставити
довільну назву шаблону, а через нового виконавця — відкрити чужому користувачу свій запуск; прямий `update` дає змогу
підробити `done_at`.

## Рішення

- `authenticated` має на `runs` і `run_tasks` лише `select` (під політиками видимості `private.can_see_run`);
  `insert`/`update`/`delete` не видано, політик на запис немає.
- Запуск: `private.launch_run(...)` — `security definer`, `set search_path = ''`, явні перевірки всередині (RLS у ній не
  діє): роль `manager`/`admin`, назва випадку 1–100 символів, шаблон існує, кожен призначений виконавець — `manager` чи
  `admin`; запуск і всі задачі — одна транзакція. `public.launch_run(...)` — тонка обгортка `security invoker` для
  Data API (схема `private` не відкрита).
- Позначка: `private.mark_task_done(task_id)` — `security definer`: дозволено виконавцю, менеджеру запуску й
  адміністратору; лише `to_do` → `done`, `done_at = now()`, `done_by = auth.uid()`; повторна позначка «done» нічого не
  змінює; інакше — `NOT_ALLOWED`. Обгортка `public.mark_task_done` — `security invoker`.
- Тригер завершення запуску (`private.refresh_run_status`) — без змін.

## Розглянуті варіанти

- Лишити `security invoker` + політики й додати в політику `insert` перевірку «запуск щойно створений» — немає надійної
  ознаки «щойно» без додаткового стану; складніше й крихкіше.
- Тригери `before insert`, що звіряють рядок із шаблоном, — дублюють логіку функції й однаково не закривають `update`
  `done_at`.

## Наслідки

- Записати дані можна лише через дві функції; права перевіряються в одному місці кожна.
- Функції `security definer` мусять самі перевіряти все, що раніше робила RLS — це покривають тести правил
  (`src/lib/runs/*.test.ts`) і `db-check` (міграції на чистій базі).
- Нова операція запису в наступних зрізах — нова функція в `private` за тим самим шаблоном.
